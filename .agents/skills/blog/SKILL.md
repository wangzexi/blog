# Blog

把写作、内容组织和发布视为同一个工作流。先判断内容是否公开，再写作或操作文件。

## 坚持核心认知

- 将 `space` 作为唯一源码仓库。
- 将 `blog/` 作为公开博客的唯一编辑位置。
- 将 `wangzexi/blog` 视为 GitHub Action 生成的公开内容副本。
- 将 MinIO 的 `sites/zexi.me/` 视为 Astro 生成的网站产物。
- 将 `static` 视为按域名读取并返回 MinIO 对象的服务。
- 不要直接修改或手工同步 `wangzexi/blog`、MinIO 或 `static`。

把内容放进 `blog/` 就等于决定公开。推送到 `master` 后，GitHub Action 会发布它。把尚未决定公开的材料放在 `inbox/`；把退出当前作品维护范围但仍需长期保留的资料放在 `archive/`。

不要使用 draft 标志、发布白名单或单独的发布命令。不要把私密内容放进 `blog/` 的任何位置。

## 组织文章上下文

为每篇公开文章使用一个顶层目录：

```text
blog/<文章目录名>/
├── README.md
├── assets/
└── refs/
```

- 用 `README.md` 保存最终文章和作者整理出的线性阅读路径。
- 用 `assets/` 保存正文引用的图片等资源，正文使用 `](assets/<文件名>)`。
- 用 `refs/` 保存原始材料、讨论记录、历史稿件、实验代码和写作过程；需要分类时在其中建立 `drafts/`、`repos/` 等子目录。
- 只在文章顶层使用 `README.md`、`assets/` 和 `refs/`，不要另设顶层 `drafts/`、`repos/` 等目录。
- 不要把密钥、隐私信息或不宜公开的参考材料放进上下文包。

让 `README.md` 至少包含：

```markdown
---
created_at: "YYYY-MM-DD HH:mm:ss +0800"
updated_at: "YYYY-MM-DD HH:mm:ss +0800"
---

# 文章标题
```

新文章同时设置两个时间。修改文章时保留 `created_at`，只更新 `updated_at`。使用 Asia/Shanghai 的真实时间，不猜测时间。

让文章目录名决定 URL。目录名可以与 H1 相同；修改标题不要求修改目录。重命名目录会改变 URL，当前静态服务不会为旧地址创建重定向。

## 理解两个发布结果

GitHub 发布整个 `blog/`：

- 完整保留每篇文章的 `README.md`、`refs/` 和 `assets/`；
- 让读者或 AI 既能阅读作者整理出的主线，也能基于整个上下文继续探索。

zexi.me 发布网站：

- 只渲染 `blog/` 下含 `README.md` 的顶层文章目录；
- 复制每篇文章的 `assets/`，保证正文资源可以访问；
- 不把 `refs/` 变成网站页面。

## 写作

### 起草

1. 在 `inbox/<文章名>/` 中组织尚未公开的内容。
2. 把对话记录、链接、背景材料和历史稿件放进 `refs/`。
3. 把正文图片放进 `assets/`。
4. 在 `README.md` 中完成最终正文。
5. 除非用户明确决定公开，否则留在 `inbox/`，不要移动到 `blog/` 或推送。

### 保持一条主线

- 开篇就把主线收窄到一句话，让读者立即知道文章讲什么、不讲什么。
- 砍掉主线之外的一切，即使它正确或有趣。判断标准不是“对不对”，而是“在不在线上”。
- 同一个观点只保留一次。以最终稿比初稿短约四分之一为参考，缩短文章但不损失信息。

### 写好开篇与收尾

- 能用公式或等式点核时，把全文压成一行放在最前面。
- 先给结论，再逐层展开。
- 用结尾回收开篇的核心词或公式，再落到一句有记忆点的话。
- 不要把收尾小标题写成“总结”。

### 用问题和例子展开

- FAQ 等章节优先使用问题式小标题。
- 在问题下先给极短直答，再解释。
- 把抽象描述换成一次真实的执行轨迹。
- 让例子贴近工程师日常、自洽且可验证；确保算术、事实和技术归属准确。
- 用“过去怎样、现在怎样”的对比建立论点。
- 能压成一行代码的概念，不要写成一段空泛描述。

### 保持排版节奏

- 单句成段，一段只讲一个点并适当留白。
- 列举两项以上时使用列表。
- 用代码块画 ASCII 关系图，不把示意代码伪装成真实实现。
- 用 blockquote 放外部数据和原文引用，与正文分隔。
- 删除没有独立信息量的标题层级。
- 连续标题之间不要插入空话；在正文段落与下一标题之间保留呼吸。
- 用水平分割线和“附录：”前缀承载非主干细节。
- 删除引导句和语气词，直接进入内容。
- 让加粗的标语句独占一行，并在前后留白。
- 适合时用对照表收尾，避免重复列表；按文章语气选择正向或反事实对照。

### 统一措辞和命名

- 优先使用正向表达。
- 软化缺少充分证据的绝对化强主张。
- 让标题、开篇主语和文章立意对齐。
- 严格核实技术归属、名字、数字和出处。
- 反复炼字，增强画面感和节奏。
- 为核心概念选择统一的英文锚点，全文只用一个叫法。
- 能不用术语就不用，不要求读者额外查定义。
- 让章节标题形成体系，使用同一套句式；连读标题时应能看见文章大纲。
- 主标题优先使用“钩子：动作”的双段式。

### 保持写作指纹

- 建立可跨篇复用的表达“弹药库”，对同一概念稳定使用同一套核心比喻和说法。
- 用物理或工业过程类比抽象软件概念。
- 为断言提供具体名字、数字和出处，不写空泛的“研究表明”。
- 像写代码一样写文章：保持单一职责、消除重复、统一命名、拒绝魔法术语、让断言有证据。

不要把这些风格机械套用到代码注释或需要完整背景铺垫的教程文档。根据文章目标取舍，但保持准确、简洁和可验证。

## 维护公开文章

### 发布

1. 确认用户已经决定公开。
2. 将完整文章目录移到 `blog/<文章目录名>/`。
3. 检查 frontmatter、H1、图片链接、上下文结构和公开边界。
4. 按“验证与推送”执行。

### 修改

直接编辑 `blog/<文章目录名>/`。保留 `created_at`，更新 `updated_at`。先验证；只有用户要求发布或任务明确包含发布时才推送。

### 重命名

先说明目录重命名会改变公开 URL，并检查站内链接。用户确认修改 URL 后再移动目录；若只修改标题，只改 H1。发布后同步程序会清除旧产物，但不会保留旧 URL。

### 删除

把删除视为同时影响下一版 `wangzexi/blog` 和 zexi.me 的操作。只有用户明确要求时才删除，并先确认精确目录。用户仍想长期保存时移入 `archive/`，不要擅自销毁。

## 验证与推送

在仓库根目录检查精确改动：

```bash
git status --short
git diff -- blog
```

本地验证网站：

```bash
cd .github/actions/publish-blog
npm ci
BLOG_CONTENT_DIR=../../../blog npm run build
```

依赖未变化且已经安装时可以省略 `npm ci`。修正全部构建错误后，只提交任务范围内的文件并推送到 `master`。

推送后检查 `Publish blog` workflow。把以下结果作为发布成功标准：

- `wangzexi/blog` 与 `space/blog/` 的公开内容一致；
- Astro 构建成功；
- MinIO 同步成功；
- 目标文章 URL 和所引用资源能正常访问。

相同文件由同步程序跳过，已删除产物由同步程序清理，不要手工登录 MinIO。

## 排查发布

沿发布链路定位问题：

```text
blog/ → GitHub Action → wangzexi/blog
                         ↘ Astro → MinIO sites/zexi.me → static → zexi.me
```

内容副本异常时检查 Action 的 Git 同步步骤；网页异常时检查 Astro 构建、MinIO 同步和最终 HTTP 响应。修复源码或发布流程，不要通过直接修改产物绕过根因。
